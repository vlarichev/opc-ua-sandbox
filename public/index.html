Browse Node Tree

An OPC-UA server organises all its data in a tree of nodes — think of it like a folder structure on a hard drive. Each node is one piece of data: a sensor reading, a setpoint, a machine status. Browse lets you open that tree and explore what's inside.

We start at the root — the very top of the tree. Click any folder to open it, or click a leaf node to see its raw server response on the right. The ns=2;s=… labels are the unique addresses OPC-UA uses to identify each node.

Read is the most common OPC-UA operation — you're asking the machine: "what is the current value of these sensors right now?" You can request multiple nodes in a single call and get all values back at once, which is much more efficient than asking one by one.

Select the nodes you're interested in below, then hit Read Values. Each result includes the value, its data type, a quality code (Good means the server is confident in the reading), and a timestamp of when the value was last updated.

Live Code

Write sends a new value to the machine — like turning a physical dial or flipping a switch, but over the network. Not every node accepts writes; only nodes the server explicitly marks as writable (usually setpoints and controls, not sensor readings) will respond.

In this simulator, Temperature Set Point and Valve Control are writable. Try setting the setpoint to a new °C value, or toggle the valve between true (open) and false (closed). The server responds with the old and new value so you can confirm the change landed.

Polling (Read in a loop) is wasteful — your code would be hammering the server with requests even when nothing changes. Subscribe flips this around: you tell the server which nodes you care about, and it pushes updates to you only when values change. This is how real-time dashboards and alarms work in industrial systems.

Select the nodes to watch, hit Subscribe, and the live feed on the right will update every time the server sends new data. Values that changed since the last update flash blue. This simulator pushes updates every 2 seconds with small random drifts to mimic real sensor noise.

OPC-UA servers can expose methods — server-side functions you trigger remotely, like pressing a button on the machine. Unlike Read/Write which operate on individual values, a method can perform a whole sequence of actions in one call: reset a set of alarms, run a self-diagnostic, or ramp a motor to a target speed.

Pick a method from the list. Some take input arguments (e.g. a target RPM), others run with no inputs at all. The server executes the logic and returns output arguments — in this simulator try Run Diagnostics for a quick system health check, or Reset Alarms to clear the high-temperature flag.

Before your application can talk to an OPC-UA server, it needs to know how to connect — which URL to use, and what level of security the server requires. GetEndpoints is the handshake step: you call it without logging in, and the server tells you everything your client needs to establish a proper session.

The response lists one entry per supported configuration. Security Mode tells you whether messages must be signed and encrypted. Security Policy specifies the exact encryption algorithm (e.g. Basic256Sha256). Real OPC-UA clients call this automatically during connection setup — here you can inspect it directly.

What is OPC-UA?

OPC UA (Unified Architecture) is the communication backbone of modern industrial systems — factories, power plants, and SCADA platforms all use it to exchange data between sensors, controllers, and software. Think of it as an API, but for machines.

Every piece of data lives in a node — a temperature sensor, a valve, a motor speed. Nodes are organised in a browsable tree and each has a unique address called a Node ID.

Anatomy of a Node ID

ns=2 ; s=Temperature.Sensor1
ns — Namespace

A numeric prefix that says who owns this data. ns=0 is always OPC-UA's own infrastructure (the server itself). ns=1 might belong to a Siemens PLC, ns=2 to an ABB controller or — as in this simulator — to your own plant's custom data model. Each vendor or system gets its own namespace so IDs never clash.

s= — String identifier

The address of this specific node within its namespace. s= means it's a human-readable string path. You'll also see i= (a compact integer, e.g. ns=0;i=85 is the standard "Objects" folder) — servers use integers internally for efficiency, strings for readability.

Six request types to explore

Browse
Navigate the node tree like a filesystem. Click any folder to drill in, use the breadcrumb to go back.
Read
Select one or more nodes and fetch their current values in a single request. The raw OPC-UA response is shown on the right.
Write
Push a new value to a writable node — try toggling the valve or changing the temperature setpoint.
Subscribe
The server streams live updates every 2 seconds. Values flash blue when they change — like a real OPC-UA monitored item subscription.
Call Method
Invoke server-side functions: reset all alarms, set motor speed to a target RPM, or run a diagnostics check.
Endpoints
Discover what security policies the server advertises — None vs. SignAndEncrypt, security profile URLs, etc.
Tip: Watch the Activity Log at the bottom as you click — every request and response is recorded with a timestamp and status code.
